# Memetic State supporter utility

## Recommendation

Start with a supporter program and offchain product credits. Specify the eventual token utility now, but activate it only after paid or high-frequency workflows exist. This creates a credible path for supporters without forcing the token to invent demand.

If a PONS launch proceeds, use one flagship stock-token pair—NVDA—while keeping the product PONS-wide. The single pair gives the launch a concise story; the engine remains the broader business.

## Design principle

The token should meter scarce services and coordinate useful contributions. It should not determine truth, buy ranking, gate raw public evidence, or promise passive returns.

## The concise answer

> The Memetic State token meters scarce intelligence services: watch slots, alert delivery, generated reports, historical exports, API capacity and team seats. Supporters can also build reputation by improving metadata and proposing coverage. Canonical evidence, methodology, integrity and rankings remain public and cannot be bought.

This is the answer to use with prospective supporters. The token is tied to recurring product consumption, not to a vague promise that attention will make it valuable.

## Product flywheel

1. PONS users discover open, verifiable market intelligence.
2. Repeat users consume scarce services: watches, alerts, reports, exports and API calls.
3. Supporters lock tokens for renewable product capacity or pay normally for the same capabilities.
4. Contributors improve metadata, coverage proposals and public-data bounties, earning non-transferable reputation.
5. Better coverage and distribution attract more researchers, launch teams and integrations.
6. Increased usage creates more demand for capacity and funds deeper coverage.

The flywheel must remain useful if token price is ignored.

## Four utility primitives

### 1. Founding identity

- Time-weighted supporter status rather than balance-only status.
- Early access to new research workflows.
- Private build/research channel and structured feedback sessions.
- Public or pseudonymous supporter mark, opt-in only.

Start this as an offchain Founding Signal pass. It tests whether identity and access are valued without requiring a token.

### 2. Product capacity

Locking utility can unlock a monthly allowance of scarce services:

- Additional alert rules and delivery channels.
- Deeper report generation.
- Larger historical exports.
- API and webhook capacity.
- Team seats or shared workspaces.

Allowances should be expressed in auditable product units—for example 25 active watch rules, five delivery routes, ten generated reports, 100,000 export rows or a defined API request budget. Exact tiers must be derived from measured infrastructure cost and user behavior before launch.

The allowance should be predictable and denominated in product units, not advertised as a financial return. Users must also be able to buy the same workflow with normal payment methods where legally and operationally appropriate.

### 3. Contribution rights

Supporters can earn reputation by doing verifiable work:

- Propose missing token identities or corrected metadata.
- Flag suspicious relationships for review.
- Request coverage of a new factory, pair, or protocol.
- Write evidence-backed annotations that survive moderation.
- Sponsor public data bounties for a clearly defined integration.

Reputation should launch before transferable rewards. Canonical data remains determined by chain evidence and reproducible rules; community contributions add context and priorities.

### 4. Coordination rights

After a real contributor base exists, supporters may signal on:

- Which habitats or protocols receive the next integration.
- Which public research bounties the community treasury funds.
- Which alert templates or reports become public goods.
- Non-critical methodology proposals, subject to published review and versioning.

No vote can rewrite historical facts, suppress a negative signal, or purchase placement.

## Activation gates

Do not activate token-dependent utility until all applicable gates pass:

| Gate | Minimum evidence |
| --- | --- |
| Reliability | Four weeks of dependable collection, explicit lag status, and no unresolved integrity incident |
| Habit | 100 weekly returning researchers or an equivalent high-signal cohort |
| Demand | 20 users repeatedly use alerts/exports, or 3 teams use the API each week |
| Payment | At least 10 users have paid for the underlying workflow without token incentives |
| Contribution | 25 useful, moderated metadata/coverage contributions from at least 10 people |
| Legal | Specialist review of token structure, distribution, marketing, jurisdictions, and access controls |

These are decision gates, not promises or launch-date targets.

## Incentive loop

1. Open evidence attracts researchers.
2. Useful research and alerts create recurring product demand.
3. Supporters receive identity, access, and contribution rights.
4. Contributors improve metadata, coverage, and distribution.
5. Better coverage makes the public product more valuable and creates more paid workflow demand.

The loop must still work if the token price is ignored.

## Launch sequence

1. **Complete:** publish the utility specification and exclusions.
2. **Complete:** ship Entitlements v1 with managed account identity, optional wallet proof, durable grants, usage accounting and five free cross-device Watchtower slots.
3. Open the Founding Signal supporter program without a transferable token.
4. Track which benefits are actually used for 30 days.
5. Ship ordinary paid product credits in a controlled beta.
6. Complete legal, security, contract and jurisdiction reviews.
7. Only then decide whether a PONS/NVDA token launch improves the loop.

The implementation boundary is documented in `entitlements-v1.md`.

## Non-negotiable exclusions

- No guaranteed returns, revenue share, APY, or “number-go-up” marketing.
- No undisclosed paid placement or score manipulation.
- No requirement to hold the token to verify canonical facts.
- No large balance advantage in factual moderation.
- No retroactive promise that offchain points will convert into tokens.
- No token launch before contract, treasury, distribution, sanctions, and jurisdiction controls receive professional review.
